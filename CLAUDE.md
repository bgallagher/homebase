# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Rackoon is an agentless SSH server manager for self-hosters (Docker Compose + Tailscale). Mac app first (SwiftUI), then iPhone, then Android. Product scope, MVP requirements (M1–M12) and phase gates are in [docs/PRD.md](docs/PRD.md). Only the MVP is scoped in detail. Work proceeds in approved stages (Stages 0 to 3 done: bootstrap, SSH transport + terminal spike, Overview/attention, saved servers + host-key trust, terminal tabs, Docker); do not build ahead of the stage the user has approved.

## Commands

Run from the repo root unless noted. In interactive zsh, don't paste commands with trailing `# comments` (they become arguments).

```
python3 tools/test-pty-relay [--ssh <host>]  # end-to-end tests of the output-highlighting relay under a real pty (build first)
python3 tools/check-spec                  # validate spec/ (JSON parses, every command has fixtures + expected output)
cd apple && swift build --product RackoonMac
tools/make-app [version]                  # builds build/Rackoon.app (ad-hoc signed, not notarized; bundle id com.bgallagher.rackoon)
cd apple && swift run RackoonMac         # launches the Mac app window (Ctrl+C to quit)
cd apple && swift test                    # needs full Xcode with its licence accepted (XCTest)
cd apple && swift test --filter ModelsTests/testServerRoundTripsThroughJSON   # single test
```

```
tools/capture-fixtures <ssh-host> <command-id> <name>   # save a real command's output as spec/fixtures/<id>/<name>.out.txt
cd apple && swift run rackoon-probe <host> overview    # headless two-poll check of ServerSession against a real host
cd apple && swift run rackoon-probe <host> updates     # apt pending/security/held counts (read-only, from apt's local cache)
cd apple && swift run rackoon-probe <host> docker      # Docker poll + harmless action checks against a real host
cd apple && swift run rackoon-probe <host> logs <container>  # stream logs 4 s, cancel, check no remote process is left
cd apple && swift run rackoon-probe <host> compose-test  # REAL pull/update/rebuild/recreate/read-only checks on a throwaway stack it creates and removes under /tmp (never touches your stacks)
cd apple && swift run rackoon-probe <host> file-test     # REAL read/validate/save of compose and .env on a throwaway stack under /tmp (creates and removes it)
cd apple && swift run rackoon-probe <host> hostkey     # unknown -> trust -> tampered flow, using a throwaway known_hosts
```

No linter or formatter is configured yet (`swift-format` is not installed). CI is `.github/workflows/ci.yml` (check-spec on Linux; `swift test`, build and `tools/make-app` on `macos-26`, because SwiftTerm 1.99 needs Swift 6.2+ and on an older runner SwiftPM silently fell back to SwiftTerm 1.20.0). Every push uploads `Rackoon-<version>-macos-arm64.zip` plus a `.sha256` as the `Rackoon-macOS-arm64` workflow artifact (14 days); pushing a `v*` tag also publishes them as a GitHub Release (Apple silicon, ad-hoc signed, not notarized, so first launch needs right-click Open). Notarizing needs a Developer ID certificate and secrets, which are not set up.

Xcode is installed on the dev machine. There is no `.xcodeproj` yet. The Mac app is a SwiftPM executable target, which needs the `AppDelegate` activation-policy workaround in `RackoonApp.swift` to show a window under `swift run`. A real Xcode project is needed before signing and notarizing.

## Architecture

**Two native cores kept in parity by a shared spec.** The server logic (shell commands, text parsers, attention rules) is small. It is implemented twice: Swift in `apple/` and, in Phase 4, Kotlin in `android/`. `spec/` is the language-neutral source of truth, so edit `spec/` first and make platform code follow:
- `spec/commands.json`: every shell command we run on a server (id, script, timeout, distros).
- `spec/models.schema.json`, `spec/attention-rules.json`: model shapes and the needs-attention rules.
- The Swift command string (`ServerSession.overviewCommand`) must equal the `script` in `commands.json`; a test enforces it. Edit both together.
- `spec/fixtures/<command-id>/NAME.out.txt` + `NAME.expected.json`: captured real output and the expected parse. Every platform's parsers must match these golden files. `tools/check-spec` fails if a command has no fixtures or a fixture has no expected output.

**Layering (same on every platform):** UI → view model/state → services → `SSHTransport` → SSH implementation.
- `RackoonCore` (`apple/Packages/RackoonCore`) is Foundation-only and must never import SwiftUI, AppKit or `Process`. It defines the `SSHTransport` protocol (`run`, `stream`) that every transport implements. Services take a transport by injection, so tests use a fake that replays fixtures.
- `RackoonSSHSystem` is macOS-only. `OpenSSHTransport` wraps `/usr/bin/ssh` (ControlMaster, BatchMode) so `~/.ssh/config` and ssh-agent work. An embedded-SSH transport (App Store, iOS, Android) swaps in later without touching Core.
- `RackoonMac` (`apple/Apps/RackoonMac`) is the thin SwiftUI app. It depends on both packages.
- The single `apple/Package.swift` uses custom `path:` entries into `Packages/*/Sources/*`, so the layout is not the SwiftPM default.

**Design constraints to keep Android and the App Store possible:**
- No Mac-only assumptions in Core. `~/.ssh/config` parsing is a Mac-app feature that produces plain `Server` models.
- Parsers stay simple (line/column splitting, or JSON from `docker ps --format json`) so they port 1:1 to Kotlin.
- `ServerSession` (Core actor) owns one server's transport, the 5 s poll loop and the last good `ServerState`. A failed poll keeps the old data and sets `error`. CPU % needs two readings, so `Overview` carries raw `/proc/stat` counters and `cpuPercent(since:)` does the delta. `ServerModel` (Mac app) bridges the actor to SwiftUI; views never call SSH directly. `Attention.evaluate` is a pure function of an `Overview`.
- Persistence: `ServerStore` (Core) writes `servers.json` and per-server cached snapshots under `~/Library/Application Support/Rackoon/`. Secrets never go there. The app was called Homebase until it became Rackoon: `ServerStore.defaultStore()` copies a legacy `Homebase/` folder once, and `RackoonApp` copies the old `HomebaseMac` defaults keys once; both leave the old data in place. On select, `AppModel` paints the cached snapshot immediately (`ServerState.isStale`) and replaces it on the first successful poll.
- Host keys: `HostKeyVerifier` (SSHSystem) runs ssh with `StrictHostKeyChecking=yes`. Unknown key -> user sees fingerprints and confirms -> exactly the scanned lines are appended to known_hosts. Changed key -> blocked, never offered for acceptance. `AppModel` only polls the selected server.
- `Server.host` is whatever ssh connects to (hostname, IP or ~/.ssh/config alias). Imported servers keep the alias as `host` so ssh applies the rest of the entry.
- Terminals: `TerminalStore` holds each server's `TerminalTab`s; a tab owns its SwiftTerm `LocalProcessTerminalView` (not SwiftUI), so sessions survive switching screens, tabs and servers, and end only on tab close, server removal or quit. Tabs run `ssh -t` over the same ControlPath as `OpenSSHTransport`, so a new tab reuses the open connection (about 0.17 s vs 0.8 s). Cmd+T / Cmd+W are menu commands (`TerminalCommands`) that replace File > Close and fall back to closing the window when no terminal is showing.
- Docker: `DockerSession` (Core actor, polls every 10 s only while the Docker screen is open, because `docker stats` takes ~2.5 s) parses `docker ps -a` + `docker stats` into stacks grouped by compose project label. Actions (`start/stop/restart`) and logs only accept a hex container id (`DockerSession.isContainerID`), since the id is interpolated into a remote shell command. The Overview command also lists unhealthy container names, which feed the attention strip; each chip links to its `fix` screen.
- Streams (`OpenSSHTransport.stream`, used for logs) deliberately use their own connection with `-tt`, not the shared ControlMaster: stopping a stream sends Ctrl-C through the pty, and tested behaviour is that Ctrl-C reaches the remote command on its own connection but not through a multiplexed one. Merely killing the local ssh leaves `docker logs -f` running forever on Tailscale SSH servers.
- Fixtures from real servers must be sanitized before committing (IPs, private container names, emails). `spec/fixtures/**/raw-*` is git-ignored for raw captures. Golden files may be generated with `RACKOON_WRITE_GOLDEN=1 swift test`; review them by hand.
- Themes drive the whole app. `apple/Apps/RackoonMac/Resources/themes.json` (hex strings; loaded via `Bundle.module`; validated by `ThemeCatalog` in Core and `tools/check-spec`) holds 45 themes: Rackoon Dark/Light are ours, 43 come from the open iTerm2-Color-Schemes collection (MIT) via `tools/import-themes` (deterministic, fetches only raw.githubusercontent.com, writes `Resources/SOURCES.md`). Do not script-download from terminalcolors.com: its `robots.txt` disallows `/downloads/`. `AppearanceStore.shared` (`@MainActor @Observable`) holds the selection (`"automatic"` by default = Rackoon Dark/Light following macOS via KVO on `NSApp.effectiveAppearance`, which only reflects the system while `NSApp.appearance` is nil, so `recompute()` sets/clears the override first and reads the system value second; or a theme id), the resolved theme, and the `AppPalette` derived from it (`AppPalette.derive` in Core: surfaces are stepped from the theme background; text/accent/status colours are clamped to minimum WCAG contrast; a test runs over every bundled theme). `Theme.*` tokens are computed from that palette, so views update only if they read tokens inside `body` (do not cache colours in `@State` or AppKit views). The root view sets `.tint`, `.preferredColorScheme` and `NSApp.appearance` so system controls and sheets match. Terminals are recoloured via `TerminalStore.applyTheme` (`onChange(of: resolvedTheme)`). The picker is the Appearance row at the bottom of the sidebar (`AppearancePicker` popover), which also holds the Highlight output switch.
- Terminal output highlighting: SwiftTerm's `LocalProcessTerminalView` feeds pty output to the terminal internally (private adapter, no hook, and `inputSender.replaceDelivery` is internal), so output cannot be intercepted in-process without replacing the view. Instead each tab runs `rackoon-pty -- /usr/bin/ssh ...` (`apple/Apps/RackoonPTY`): a pty relay that copies input through untouched, forwards resizes/signals/exit status, and passes ssh's output through `TerminalOutputFilter` (Core, pure, heavily tested), which wraps IPs, error/warning/success words and high percentages in SGR colour pairs from the active theme's palette. The filter never touches escape sequences, the alternate screen (vim/htop), or text a program has already coloured, and skips matches that touch a chunk edge. The relay is located next to the app executable (built as a dependency of RackoonMac); if missing, tabs run ssh directly. Tabs always start through the relay (with `--no-highlight` if the setting is off), and the Highlight output switch takes effect immediately on open tabs: the app sends SIGUSR1 (on) / SIGUSR2 (off) to the tab's `shellPid`, which is the relay. The relay installs its signal handlers before forking, then publishes `/tmp/rk-<uid>/relay-<pid>.ready` (removed on exit); `TerminalTab.setHighlight` only signals a relay whose marker exists (those signals terminate a process without handlers) and retries for a few seconds while it starts, guarded by a per-launch generation so a stale task cannot signal a newer relay. Signal handlers also poke a self-pipe so `poll` wakes immediately. The setting reaches tabs through `onChange(of: appearance.highlightOutput)` in `ContentView`, not a global callback (a `@State` default like `TerminalStore()` is constructed on every parent re-evaluation and all but the first instance are discarded, so constructors must have no side effects). The filter tracks escape state even while off, so switching on mid-vim is correct. Run `tools/test-pty-relay` after touching the relay or filter.
- Updates: `UpdatesSession` (Core) runs the read-only `updates` command (`apt list --upgradable`, held packages, cache age, reboot flag) and `UpdatesParser` turns it into an `UpdatesSnapshot`; a package is security if any of its suites ends in `-security`. The Overview command also carries a `##security` count so the attention strip can show `security_updates` without opening the Updates screen. The Updates screen is `UpdatesScreen` + `UpdatesModel` (reads on open and after each action, no polling; Refresh Lists / Install All / Install Security Updates go through the confirm sheet). The Overview command also carries `##updates` (total) and `##security` counts from one `apt list` call; they drive the dot on the sidebar's Updates row (`UpdateBadge`, amber if any security). `RACKOON_DEMO_UPDATES=1 swift run RackoonMac` fakes a server with pending updates (canned data, nothing is sent) so the screen and dot can be seen when the real server is up to date.
- Branding: `assets/icon/rackoon-icon.svg` is the source of the icon; `RackoonMac/Resources/rackoon-icon.png` is a 1024 px render (`qlmanage -t -s 1024`). `AppIcon` draws it in the macOS rounded-square shape for the Dock (needed under `swift run`; a real bundle should ship an .icns instead) and `AboutView` (a `Window` scene, opened from the app menu's About item) shows it.
- Compose stack actions (`ComposeAction` pull / up / rebuild (`up -d --build`) / recreate, in `DockerSession.swift`) run `cd <dir> && docker compose -p <project> -f <file> [-f <file>...] ...` from the stack's own labels (every file of the comma-separated `config_files` label, in order; `DockerContainer.configFiles`). If a project's containers disagree on directory/files, the stack gets none and the command is nil. The project name must match `^[a-z0-9][a-z0-9_-]*$`, paths must be absolute and are single-quoted with `ShellQuote` (tested through a real `/bin/sh`), and anything unsafe or missing makes the command nil, so nothing is sent. They are `.mutate` intents. The probe's docker mode checks every stack resolves with a harmless `config -q`; it never pulls or recreates. `DockerState.busyStacks` marks a stack busy by project name for the whole action (container ids change when `up -d` recreates). The UI is the ⋯ menu on each stack header (`StackCard.stackMenu` -> `DockerModel.request(_:on:)`, with `composeBlockedReason` explaining why it is disabled); Recreate is marked destructive in the confirm sheet.
- Apt actions (`AptAction` in `AptActions.swift`: refresh, upgradeAll, upgrade(packages:)) run through `UpdatesSession.perform`, which then re-reads the update list. The shell prefix uses root directly or `sudo -n` (never prompts), `DEBIAN_FRONTEND=noninteractive LC_ALL=C`, `--force-confold`, and never `dist-upgrade`/remove/autoremove. Package names are validated against Debian naming, de-duplicated and capped at 200 (`AptAction.maxPackages`; callers fall back to upgradeAll) before being joined into the command; failures are explained from stdout and stderr together (sudo's localised messages are recognised by their `sudo:` prefix). sudo/lock failures get readable messages. Unit-tested (including a real `/bin/sh` run with stub `apt-get`/`sudo`), deliberately never run against a real server. No UI yet.
- App bundle: `tools/make-app` assembles `build/Rackoon.app` (executable `RackoonMac`, the relay next to it in Contents/MacOS, SwiftPM's resource bundle in Contents/Resources, `AppIcon.icns` from `tools/make-icns.swift`, Info.plist with the version). Load bundled files through `AppResources`, never `Bundle.module` directly: its generated accessor looks beside the .app (code signing rejects unsealed files there) and traps if the bundle is missing, which crashed the first bundled build. A bundle id changes the UserDefaults domain, so `RackoonApp` copies keys from the earlier `RackoonMac`/`HomebaseMac` domains once. The Docker screen (`DockerScreen.swift`) is a grid of `StackTile` cards; clicking one opens `StackDetail` (breadcrumb, stack actions Pull/Rebuild/Restart + ⋯ Update/Recreate, a container list with Logs/Shell/Restart/Stop, and a framed right panel whose Logs tab is the live log view; the compose.yaml and .env tabs are placeholders for the editor stage). Shell opens a terminal tab running `DockerSession.shellCommand` (`docker exec -it <id> ...`, spec kind "interactive") via `TerminalStore.newTab(for:title:command:)`. Do not `pkill -x RackoonMac`: it also kills the user's own `swift run` instance; match the exact path.
- Stack files (`StackFiles.swift`, `StackFileCommands.swift`, `StackFileSession.swift`, `LineDiff.swift`; spec `file_read`, `file_validate`, `file_write`): backend for the compose/.env editor. Only a stack's own compose files and `<working_dir>/.env` are editable (`StackFiles.editable`); anything else gives a nil command. Reading is `file_read` (sha256 + base64, 64 KiB cap because content travels inside one remote command argument, base64-encoded and never as text). Checking runs the server's own `docker compose config -q` against a temp copy in the same folder (`-f` list with the edited file swapped for `"$T"`, or `--env-file "$T"` for .env), so relative paths and interpolation resolve exactly as on deploy. Saving (`.mutate`, `FileEdit` + `StackFileSession.confirm/save`) re-checks, refuses if the file's sha256 changed since it was opened (`##changed`), keeps `<file>.rackoon.bak`, preserves owner and mode (`--reference`), then `mv`s atomically. `Intent.preview` carries a readable diff for the confirm sheet because the command itself is not readable. Newer compose reports syntax errors as `at L4.C12:` and names the temp file; `ComposeIssueParser` and `ComposeIssue.naming` normalise that. Command templates are filled in one pass (`Template.fill`), never by sequential replacement. The editor UI: `StackPanel` (tabs: Logs, each compose file, .env) with `FileEditorBody` (code view, checklist, Revert / Save / Save and Redeploy) in `StackPanel.swift`; `StackEditorModel` holds one draft per opened file, checks the exact current text on the server after a 600 ms pause (`validatedText` guards against showing an old result for new text; `.env` syntax is also checked locally with `EnvSyntax`), and only enables Save when that check passed. `EditorChecks.rows` (Core, tested) builds the checklist. Save and Redeploy asks once (diff + the `up -d` command), saves, then runs `DockerModel.runDirect(.up)`. A save refused because the file changed on the server shows Reload from Server / Keep Editing; there is deliberately no overwrite. `CodeEditorView` is an NSTextView wrapper (own ruler with line numbers, bands behind changed/failing lines drawn in `drawBackground`, colours from the terminal theme via `SyntaxHighlighter`, 2-space tabs, auto-indent, smart quotes off); give it `.id(file)` so undo history is per file. Leaving a stack with unsaved edits asks first.
- System info and reboot: the Overview command has a labelled `##system` section (vendor, product, machine id, kernel, boot id, server time with offset and zone abbreviation) shown by `SystemInfoCard` (uptime and clock tick locally from the last poll). Reboot (`RebootSession` in Core; spec `reboot` and `boot_id`): a `.mutate` intent that checks `sudo -n` first (exit 5 `##no-sudo`, nothing scheduled), then schedules `systemctl reboot` two seconds out under `nohup` so the ssh command returns cleanly, and `waitForReturn` polls the kernel boot id every 4 s until it DIFFERS from the one read before (a successful connection alone proves nothing, the old system answers for a moment) or 10 minutes pass. `RebootFlow` (AppModel.swift) drives it and `RebootProgressBanner` shows waiting / back / timed out / failed; failing polls are not shown as errors while it is active. `RACKOON_DEMO_REBOOT=1 swift run RackoonMac` fakes a reboot that returns after ~15 s (nothing is sent). The real reboot has been tested only with fakes: never reboot the user's server to test it.
- Live output of stack actions: `DockerSession.performStreaming` runs the same compose command as `perform`, but through `transport.stream` (own ssh connection with `-tt`, so compose draws its normal redrawing progress) wrapped by `StreamedCommand` (`stty cols/rows` to match the viewing terminal, run in a subshell, print `##rackoon-exit:<n>`; spec `stream_wrap`), because a streamed ssh yields output but no exit status. `StreamOutputParser` strips the marker (holding back a possible partial marker across chunks) and yields the code; no marker means cancelled or dropped and is never success. It works on unicode scalars: Swift treats `\r\n` as ONE Character, which once made real pty output never match (fakes hid it; the real-server `compose-test` caught it). `Utf8Chunker` (used by `OpenSSHTransport.stream`) keeps multi-byte characters intact across read boundaries. The app side: `StackOutput` (per run: chunks, phase, terminal size) is fed in order through an AsyncStream; `OutputTerminalView` is a read-only SwiftTerm `TerminalView` (shared `applyRackoonTheme`), whose reported size becomes the remote pty size before the command starts; the detail page's Output tab opens when a run starts and has Cancel (cancelling the task sends Ctrl-C to the remote command) then Close. Container-level start/stop/restart stream through the same core (`DockerSession.stream`, shared by both `performStreaming` overloads; the output run is keyed by the container's project, or "Standalone"). Apt installs stream too: `UpdatesSession.performStreaming` (read-only list reads stay on `transport.run`), with sudo and apt-lock failures recognised from the streamed text via `ANSI.strip` + `AptAction.explain`. The streaming loop is shared (`StreamRunner` in Core, used by `DockerSession.stream` and `UpdatesSession`), and on the app side `ActionOutput` (one run: scope, chunks, phase; `ActionOutput.launch` does the size handshake, ordered event delivery and completion) plus `ActionOutputPanel` (header with Cancel/Close over `OutputTerminalView`) serve both the Docker detail page's Output tab and the Updates screen. `rackoon-probe <host> apt-stream-check` streams `apt-get -s upgrade` (simulation, changes nothing) through the real wrapper. Under `RACKOON_DEMO_UPDATES=1` the fake transport also streams fake apt output.
- Mutations go through `ActionPolicy` (Core, `ActionPolicy.swift`): each state-changing command is an `Intent` (risk `.mutate`), the service refuses it unless read-only is off and it holds a `Confirmation` for that exact command (only `ActionPolicy.confirm` mints one; `DockerSession.confirm` wraps it). Checked again at run time. The UI side is `SafetyStore.shared` (`Safety.swift`: persisted Read-only switch in the sidebar, owns the one shared `ActionPolicy` that sessions are created with) and `PendingAction` + `.confirmAction(...)` (a native-button sheet showing the exact command; confirm button reads "Run Command"). Native-styled buttons also get `.handCursor()` (native buttons show the arrow otherwise), applied to EACH button and BEFORE its `.disabled(...)`: a modifier reads `isEnabled` from where it sits, so on a group or after `.disabled` it keeps the hand on greyed-out buttons. Mutating buttons use `IconButton(mutates: true)`, which disables itself in read-only mode. Stop and Restart confirm; Start runs directly. New mutating features (pull, recreate, apt upgrade) must use it.
- Terminal auto-reconnect: `TerminalTab.ended` retries only when ssh exits 255 (connection failed or dropped; `exit` and remote command statuses are never retried), up to 5 attempts with 1/2/4/8/15 s backoff, and a session that lasted 10 s or more resets the budget. Scrollback is kept (a dim notice is fed to the view) and `TerminalScreen` shows a countdown overlay with Reconnect Now / Cancel; the manual Reconnect button clears the screen. `terminalArguments` sets `ServerAliveInterval=15` / `CountMax=3` so a dead link makes ssh exit after ~45 s instead of waiting for TCP; without it nothing ever triggers the retry. Verified by hand with Wi-Fi off/on.
- Per-container Rebuild: `ComposeAction.rebuild.command(for:service:)` (spec `compose_rebuild_service`) runs `up -d --build --no-deps <service>`; only `.rebuild` accepts a service, which must pass `isServiceName` and exist in the stack. The Rebuild link on a container row (`DockerModel.requestRebuild`, via the confirm sheet) streams into the Output tab. Unit-tested and run by hand on the real server (xrray-net web, a Dockerfile-built service); a service with no build section is a no-op for compose.
- Add container (design: Docker page canvas, `project/Add.dc.html`; read it before changing the page): a form (`ContainerSpec`: name, image, port/volume/env rows, restart policy; `ContainerSpec.blockingProblem` and the per-row `*Problem` helpers) writes compose YAML (`yamlLines`, bare `no` is quoted because YAML reads it as false) and `.env` lines (`EnvMerge`, values quoted safely). New stack: `NewStackPlan` -> `<parent>/<name>/compose.yaml`; `NewStackDefaults.parentDirectory` learns the folder from the most common parent of existing stacks' `working_dir` (else `/opt/stacks` for root, `/home/<user>/stacks`). `NewStackCommands.check` (spec `stack_new_check`) validates in a `mktemp -d` scratch folder and never touches the real one; `create` (spec `stack_create`) refuses an existing folder (exit 3), writes the files (.env mode 600), runs `docker compose config -q` in place and removes everything it made if that fails (exit 4). Existing stack: `ComposeInsert.adding` appends the service at the end of the `services:` block as new lines only (follows the file's indent, refuses inline `services: {}` and duplicate names) and `EnvMerge.merge` appends only variables `.env` does not define; both are saved through `StackFileSession` (sha-guarded, .bak, .env first so a refused compose save leaves only a spare variable). Checks (`ContainerChecks`, spec `image_exists` = `docker manifest inspect` on the server, `listening_ports` = `ss -H -tln`): YAML/compose result collapsed to one row, image found, each host port free (names the owner container, suggests a free port), container name free. Deploy needs the exact current text checked and no failing row. The right-hand editor is editable and two-way for a new stack: typed or pasted compose text is read back into the form by `ComposeFormParser` (line based, single service, inverse of `yamlLines`; a port host field may be `[address:]port`, e.g. `${TS_IP}:8080`). The text stays as written (a hand edit stops the form from rewriting the file) until the form is edited; if the file uses anything the form can't show (`lossless == false`: comments, other keys, literal env values, /udp ports, other top-level keys) the form is locked as a read-out. Reset to form regenerates the file from the form. `AddContainerModel`/`AddContainerScreen` (Docker overview -> Add Container); Save only writes files, Create and start also runs `up -d` (streams into the stack's Output tab, which `StackDetail` opens on). A new stack with no containers is invisible to `docker ps`, so `DockerModel.createdStacks` remembers it (shown "Not started") until it appears; scanning the stacks folder for never-started stacks is not built. `rackoon-probe <host> newstack-test` runs the real create scripts on a throwaway folder under /tmp (probe not run yet). Verified by hand 2026-10-10: a pasted hello-world stack (nginxdemos/hello bound to the Tailscale IP via `${TS_IP}` in .env) was created and started from the UI and answered over the tailnet; Existing stack mode and Save only are not yet tried on the real server.
- Not built yet: Keychain secrets (BatchMode means password auth does not work; keys and ssh-agent do), editing a server.
- The server stays untouched: no agent, standard SSH commands only (Debian/Ubuntu and apt for the MVP).
